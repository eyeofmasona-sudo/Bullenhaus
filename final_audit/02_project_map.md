## Layer boundaries observed

- **Server/client boundary is correctly drawn for the privileged operations that matter**: balance-affecting actions (`approve_deposit`, `approve_withdrawal`, `execute_spot_trade`) live in `SECURITY DEFINER` Postgres functions with explicit internal role/ownership checks, not in client-trusted code. Staff-only HTTP actions (`api/crm/**`) re-check the caller's role server-side via `requireAdmin`/`requireCrmAdmin`/`requireCrmStaff` rather than trusting the client-side route guard.
- **Client-side route guards (`ProtectedRoute`, `AdminProtectedRoute`) are UI-only conveniences**, not the actual authorization boundary — confirmed by the point above. This is the correct pattern (defense happens at the data layer) and was independently verified, not assumed.
- **No circular workspace dependencies observed** in `pnpm-workspace.yaml`'s package list; `tsc --build` (project references) completed without a dependency-cycle error, which would otherwise surface as a `tsc --build` failure.
- **No local migration history** — the database schema exists only as live state in Supabase, not as reviewable/rollback-able files in this repo. This is a repository-completeness gap, not a runtime defect (see 04, AUDIT-009).
